## How this review was done and its limits

- Every line of every source file was read by hand. Line numbers below are for revision `ce2ab74`.
- FrostbiteGen is a Windows-only DLL. It uses `<Windows.h>`, MSVC structured exception handling (`__try`/`__except`) and runs injected into a live game. The review ran in a Linux container with no MSVC toolchain and no game binary. So:
  - **The generator itself was not built or run.**
  - Claims about the *generated SDK* that could be checked offline were checked. The relevant emitter logic was reproduced and compiled with g++ 13 (see [Appendix A](#appendix-a-reproductions)). These findings are marked **Verified**.
  - Claims that depend on the game's in-memory engine layout (for example, how Frostbite lays out reflected arrays) could not be checked against a real Mirror's Edge Catalyst process. These are marked **Unverified (engine layout)** and should be confirmed in a debugger.
- Severity reflects impact on the tool's purpose: producing a correct, compilable SDK without crashing the host game.

**Severity scale**

| Level | Meaning |
|---|---|
| **High** | Generated SDK does not compile, returns wrong addresses, or the game can crash during generation |
| **Medium** | Wrong output in common edge cases, a security weakness with a plausible path, or a large performance cost |
| **Low** | Edge cases, hygiene, maintainability |
| **Info** | Observations and documentation |

## Executive summary

FrostbiteGen has a sound core idea: it walks Frostbite's reflection data and emits ASLR-relative headers. Some details are done carefully, including SEH-guarded read helpers, cycle detection, a worker thread instead of doing work in `DllMain`, and self-unload. However, the most recent large changes added many output features without any way to check that the output compiles or is correct, and it shows:

1. **The generated SDK very likely does not compile as-is.** Three separate emitter bugs each break compilation, and all three were reproduced:
   - `Array<T>` is declared inside `namespace fb` but used unqualified in every class with an array field (G2).
   - Integral-valued float snapshots are emitted as `0f`, `1f`, `60f`, which are invalid C++ literals (G3).
   - A leaked `std::hex` stream state emits `totalMethods = 1a` in the VMT hook helper (G4).
2. **The generated memory layout is wrong whenever a class has a 64-bit integer field.** `Int64` and `Uint64` are mapped to `long` and `unsigned long`, which are 32-bit on Windows. Every later member in that class then lands 4 bytes off (G1).
3. **Several `GetInstance()` resolvers return the wrong pointer:**
   - Static in-image singletons are dereferenced as if they were pointers, so the resolver returns the vtable (G5).
   - Chains that pass through an array are one dereference short (G6).
   - The root object is often accepted by a weak heuristic and labelled with an assumed class name, without checking its real type (G10).
4. **The game can crash during generation.** The pattern scanner and many direct reads of engine memory run without SEH or page checks (R1, R2).
5. **Security:** strings read from the game's memory are written unescaped into the generated IDA and Ghidra Python scripts and the C++ headers. Anyone who can influence those strings (a malicious mod, a tampered executable, another injected module) can get code execution in the reverse-engineering tool or in the user's compiled mod (S1). The generated hook helpers also allow a heap overflow (S2).
6. **Performance:** two full-image scans call an SEH-guarded read for every byte or every 8-byte slot, and are likely to take minutes on a 100 MB+ game image (P1, P2).
7. **The README has drifted from the code.** It documents `fb::ReadChain`, `fb::PatternScan`, an "instance offset" mechanism and `m_instanceOffset`, none of which exist. README examples 4 and 5 cannot compile (D1, D2).

**Most valuable single fix:** add a CI job that generates an SDK from a small synthetic type database and compiles it. This would have caught G1–G4, G14–G16 and G21 automatically (Q8).

## 1. Security

### Threat model

FrostbiteGen runs with the game's full privileges inside the game process. It reads untrusted memory, meaning anything that is not FrostbiteGen's own data, and writes files that the user later **executes**: Python scripts run in IDA or Ghidra, and C++ headers compiled into a DLL that is then injected into the game. The trust boundary is therefore "bytes in the game's address space" → "code the user runs". Mods, repacked or cracked executables, and other injected modules can all put arbitrary bytes in that address space.

### S1 (Medium): Untrusted strings from process memory are emitted unescaped into generated code and scripts

Type names, field names and enumerator names are read from game memory and pasted directly into executable outputs:

| Output | Sinks (raw engine strings) |
|---|---|
| `SDK/ida_import.py` | `classinfo.cpp:2423`, `2430` (enumerator names), `2441`, `2467` (field names), `2478`, `2491`, all inside `'...'` Python literals |
| `SDK/ghidra_import.py` | `classinfo.cpp:2541`, `2542`, `2549`, `2560`, `2561`, `2583`, `2622` |
| C++ headers | class names `1030`, `1035`, `1115`, `1159`, `1166–1185`; enumerator names `1200`; `#include` targets `1029`, `1233`; comments throughout |

Only class names pass through `SafeReadString` (in `BuildClassList`, `classinfo.cpp:127`), and it allows every printable ASCII character, including `'`, `"`, `;`, `{`, `}`, `(`, `)` and `\`. Enumerator names (`fie->name`) and the field names used by the script generators (`GetSafeFieldData`, `classinfo.cpp:2190`) are not filtered at all.

**Impact.** A type or field name such as `x', 0)\nimport os; os.system('...')\n#` executes when the user runs `ida_import.py` in IDA or Ghidra. An enumerator named `A = 0 }; static int _ = (Payload(), 0); enum B {` injects C++ into a header that the user compiles into a mod and injects into a process. Exploitation needs control over strings in the target process, so the likelihood is low. The impact is code execution on the analyst's machine.

**Recommendation.**
- Validate every name once, when it is read, against `^[A-Za-z_][A-Za-z0-9_]*$`. Rename anything that fails (for example `Invalid_<hash>`) and log it.
- When writing Python, escape string literals properly: escape `\` and `'`, and reject control characters. Or emit the data as JSON and have the script `json.loads` it.
- Never paste a raw engine string into code. Comments are the only exception, and backslashes must be stripped there too (see G22).

### S2 (Medium): Generated `HookVFunc_Shadow` can overflow the heap

`classinfo.cpp:1862–1872` emits the following into every class header that has a captured vtable:

```cpp
static T HookVFunc_Shadow(void* instance, int index, T newFunc, int totalMethods = <N>) {
    void** shadowVTable = new void*[totalMethods];
    memcpy(shadowVTable, originalVTable, sizeof(void*) * totalMethods);
    ...
    shadowVTable[index] = (void*)newFunc;      // no bounds check
```

- **Heap overflow:** if `index >= totalMethods`, the write lands past the end of the allocation.
- **Wrong default size:** `<N>` comes from `SafeCountVTableEntries` (`structs.h:132–148`). It stops at the first entry that does not point into the module, so it can undercount (for example, a thunk into another DLL). G4 also means `<N>` is often printed in hex without a `0x` prefix, so the value is wrong even when it compiles. Any virtual call through an index ≥ `N` then reads past the shadow table.
- The RTTI Complete Object Locator at `vtable[-1]` is not copied, so `typeid` and `dynamic_cast` on a hooked object will crash.
- The shadow table is leaked, hooking twice stacks shadows, and there is no unhook function.

**Recommendation.** Bounds-check `index`, copy from `vtable - 1`, provide `Unhook`, keep the shadow table in an RAII owner, and use a vtable length that is either verified or passed by the caller.

### S3 (Low): Generated in-place hook makes vtables RWX and ignores VirtualProtect failures

`classinfo.cpp:1855–1858` uses `PAGE_EXECUTE_READWRITE` on `.rdata`. `PAGE_READWRITE` is enough, because a vtable is data. Neither `VirtualProtect` result is checked, so on failure the next line writes to read-only memory.

### S4 (Low): Over-broad SEH can turn a crash into silent corruption or a deadlock

- `GenerateBonusOutputs` (`classinfo.cpp:281–288`) wraps eight STL-heavy generators in `__try { ... } __except(1)`, which catches every SEH exception. That includes `STATUS_STACK_OVERFLOW` and faults raised while the CRT heap lock is held. If an exception is swallowed at that point, the game process can be left with a corrupted heap or a held lock.
- Under the checked-in `.vcxproj`, which does not set `/EHa`, C++ destructors do not run during SEH unwinding. Every caught fault then leaks the `std::ofstream` handle and leaves a partially written file.
- Prefer filtering to `EXCEPTION_ACCESS_VIOLATION`, and keep `__try` only around raw memory reads. The `Safe*` helpers in `structs.h` already do exactly that.

The generated `fb::Read`/`fb::Write` helpers (`classinfo.cpp:2670`, `2713`) also swallow every exception silently. That is defensible for a modding SDK, but it should be documented.

### S5 (Low): Committed IDE user file leaks a local path; `.gitignore` contradicts tracked files

`FrostbiteGen.vcxproj.user:4` contains `D:\Dumps\swbf dumps\First\starwarsbattlefront_Dumped.exe`. `.gitignore:50,56,57` ignore `*.user`, `*.vcxproj` and `*.vcxproj.filters`, yet all three are tracked. Remove the `.user` file from the index, or stop ignoring the files that are intentionally tracked.

### S6 (Info): No warning about anti-cheat for the multiplayer titles the code targets

`FindClientGameContext` hardcodes offsets for `bf4.exe`, `bf1.exe` and `starwarsbattlefrontii.exe` (`classinfo.cpp:306–313`). These are online titles with anti-cheat. The README tells users to inject with third-party injectors and gives no warning that doing so in these games can get accounts banned. Add an "offline or single-player only, at your own risk" note.

### Positive security observations

- File names are sanitized of `\ / : * ? " < > |` (`GetSanitizedClassName`, `classinfo.cpp:2850–2859`), so a type name cannot escape the `SDK\` directory through path traversal.
- JSON and Cheat Engine XML outputs are escaped (`EscapeJson`, `EscapeXml`).
- Every `Log(...)` call uses a literal format string, and `_vsnprintf` is bounded (`main.cpp:62`). There is no format-string injection.

## 2. Bugs and correctness

### 2a. Generated SDK (compile errors and wrong addresses)

#### G1 (High): `Int64`/`Uint64` emitted as `long` (32-bit on Windows), so layouts shift

`GetFixedClassName` (`classinfo.cpp:1246`, `1250`) maps `Int64 → long` and `Uint64 → unsigned long`. Windows is LLP64, where `long` is 4 bytes.

`DumpClassMembers` advances its offset by the engine's size, 8 bytes (`classinfo.cpp:1306`), so the padding before the next member is calculated as if 8 bytes had been emitted. Only 4 were. **Every member after a 64-bit integer is therefore 4 bytes too early**, and the class `sizeof` is wrong. Writing through such a member corrupts the neighbouring field.

The same mapping affects accessor types, `Offsets` users, `Call_Get_*` return types and the IDA type mapping (64-bit fields fall back to `FF_BYTE`).

**Fix:** use `<cstdint>` types throughout: `int8_t … uint64_t`. Also emit `static_assert(offsetof(C, m_X) == 0x..)` and `static_assert(sizeof(C) == 0x..)` for every member and class, so any remaining layout error fails at compile time instead of corrupting game memory.

#### G2 (High): `Array<T>` is declared in `namespace fb` but used unqualified (Verified)

`GenerateFBSDKTypes` declares `template <typename T> class Array` inside `namespace fb { … }` (`classinfo.cpp:2659–2721`). Members and accessors are emitted as `Array<...>` (`classinfo.cpp:1322`, `1324`, `1924`, `1926`), and nothing emits `using namespace fb`. **Every class with an array field fails to compile.** g++ reports `'Array' does not name a type`; see Appendix A.3. The fix is to emit `fb::Array<...>`.

#### G3 (High): `Defaults` snapshot emits invalid float literals (Verified)

`DumpDefaultValues` writes `<< std::defaultfloat << val << "f;"` (`classinfo.cpp:1499`). For values such as 0, 1 or 60 this produces `0f`, `1f`, `60f`, which are **not valid C++ literals** (a floating literal needs a `.` or an exponent before the suffix). NaN and infinity produce `nanf` and `inff`. Any reachable class with an integral-valued float field fails to compile. See Appendix A.1–A.2.

Other problems in the same block:
- The default 6-digit precision loses information; use `max_digits10` or `std::hexfloat`.
- Doubles have the same NaN/infinity problem (`classinfo.cpp:1534`).
- `char` and `unsigned char` are read with a 2-byte read (`classinfo.cpp:1513`, `1528`), which can fault on the last byte of a page.
- The struct is named `Defaults`, but it holds *live values at generation time*. If the user had god mode on while generating, `Defaults::IsGodMode` is `true`. Rename it to `Snapshot`, or document this.

#### G4 (High): Leaked `std::hex` state corrupts `HookVFunc_Shadow` default argument (Verified)

The last statement `DumpClassMembers` writes is `<< std::hex << fi->offset << std::endl` (`classinfo.cpp:1316–1327`). The stream is only reset to decimal if tail padding follows (`classinfo.cpp:1067`). `DumpVMTHookHelper` then prints `int totalMethods = " << it->second.entryCount` with no base manipulator (`classinfo.cpp:1864`).

For classes with no tail padding:
- **10–15 entries** emit `a`–`f`, which does not compile.
- **16 or more entries** emit e.g. `10`, `1a` or `20`. These either fail to compile or **silently produce the wrong (smaller) number**, which feeds directly into S2.

Reproduced in Appendix A.4: an entry count of 26 is emitted as `1a`.

**Fix:** `<< std::dec` at that line. More generally, never rely on stream state: either use a helper that formats hex numbers explicitly, or reset with `std::dec` after every `std::hex`.

#### G5 (High): Static singletons are dereferenced as pointers

`ScanGlobalsForSingletons` stores two different kinds of entry in the same map, `m_globalInstances`:
- heap singletons, where the slot holds a **pointer to** the object (`classinfo.cpp:2794`);
- static singletons, where the slot **is** the object (`classinfo.cpp:2825`).

Downstream code reads the map as follows:

| Consumer | Behaviour |
|---|---|
| `DumpInstanceResolver` (`1374–1380`) | Always emits `fb::Read<uintptr_t>(base + off)`. For a static singleton this returns the **vtable pointer**, cast to `Class*`. |
| `DumpLiveInstances` (`2877–2885`) | Reports the vtable address as the "instance". |
| Traversal chains rooted at a static singleton (`2835`) | Every descendant's `GetInstance()` starts from the vtable, so the whole subtree is wrong. |
| `DumpConsoleVariables` (`3020–3035`) | **Handles it correctly** by checking whether the value read is an in-module pointer. |

`FindClientGameContext` has the same issue in its "maybe the offset *is* the instance" path (`classinfo.cpp:327–328`): the chain is stored with `rootGlobalOffset` and later emitted with a dereference.

**Fix:** record an `isStatic` flag for each root and emit `base + off` instead of `Read(base + off)` when it is set.

#### G6 (High): Traversal chains through arrays miss a dereference

In the array branch of `BuildTraversalMap` (`classinfo.cpp:682–703`), the walk does two dereferences: `firstElem = *(obj + fi->offset)`, then `elemPtr = *firstElem`. It records only **one** step, `{offset = fi->offset}`. The emitted resolver (`classinfo.cpp:1411–1416`) performs one `Read` per step, so it returns `firstElem`, the address of the array's storage, instead of element 0.

**Fix:** record a second step (offset 0), or give steps a kind such as `{Deref, Index}` so the emitter can produce correct code.

#### G7 (Medium-High): Skipped or overlapping members silently shift the layout

In `DumpClassMembers` (`classinfo.cpp:1301–1311`, `1320`), `lastOffset` is advanced **before** the member's type is validated. When the type is invalid, the function `continue`s without emitting any bytes and without adding to `totalSize`, and every following member moves earlier.

If two fields overlap (`fi->offset < lastOffset`, which happens with unions or with a wrong `GetFieldSize`), the second is simply emitted after the first, also shifting the layout.

**Fix:** always emit something that occupies `[offset, offset + size)`, using a raw byte array when the type is unknown. Treat overlaps as an error and emit a `union` or a comment. Combine this with the `static_assert`s from G1.

#### G8 (Medium): Array field size hardcoded to 32 bytes, ignoring engine size

**Unverified (engine layout).**

`FieldInfo::GetFieldSize` returns `32` for every array (`structs.h:291–292`), and the emitted `fb::Array<T>` is `{first, last, bound, allocator}` (`classinfo.cpp:2674–2687`). The traversal code also assumes `{begin, end}` at `+0`/`+8` (`classinfo.cpp:683–687`).

In several Frostbite 3 titles, reflected array fields are a single pointer with the element count stored just before the data, which would make them 8 bytes. This could not be checked against Mirror's Edge Catalyst. Either way, the engine's own `TypeInfo::totalSize` for the array type should be the source of truth instead of a constant. If it disagrees with 32, every class with an array field has a broken layout.

#### G9 (Medium): Types classified by exact flag values instead of decoded type codes

Type kinds are decided by comparing the whole 16-bit `flags` value to hand-collected constants:
- `classinfo.cpp:253–266` (`49289`, `41`, `32809`, `53289`, `13`, `49357`, …, `69`, `29`);
- `GetFieldsArray` at `classinfo.cpp:2228`;
- `kType_Pointer = 53` and `kType_Array = 65` everywhere.

The decoding constants already exist in `MemberInfoFlags` (`structs.h:244–262`: `kTypeCodeShift`, `kTypeCodeMask`, …) but are never used. The hand-listed values make the fragility visible: `32809 = 41 | 0x8000` and `53289 = 41 | 0xC000` are the same struct kind with extra attribute bits.

**Consequences:**
- Any enum, struct, pointer or array whose flags include an attribute bit not on the list falls through to `DumpClass`, which reads `ti->fields` instead of `structFields`/`enumFields`.
- A pointer field with an extra bit is emitted as a by-value member with the pointee's size.

Related problems:
- `AnalyzeVTableMethod` compares `MemberTypeInfo::flags` with `kType_Pointer` (`classinfo.cpp:1740`), whereas everywhere else compares `TypeInfo::flags`.
- `kAlwaysPersist` and `kExposed` are both `0x2000`.
- `kBlittable = 0xFFFF8000` is defined for a 16-bit field.

**Fix:** decode the type-code bits once into an enum, and switch on that.

#### G10 (Medium): Root object can be misidentified and walked with the wrong layout

For executables without a hardcoded offset, `FindClientGameContext` works as follows:

1. It picks a class by **name only**: the largest of 15 generic candidates, including `"Context"`, `"Client"`, `"Main"` and `"Engine"` (`classinfo.cpp:371–393`).
2. It accepts the **first** global, matched by one of 11 common instruction patterns, whose object has a vtable inside the module and at least 3 sub-objects with vtables inside the module (`classinfo.cpp:471–497`, threshold at `490`). Almost any manager singleton passes this test.
3. The brute-force fallback returns the best candidate **of the first writable section** that reaches score 5, not the best across all sections (`classinfo.cpp:561–616`).

The object found is then labelled with the name-matched class. `DumpClasses` takes that label at face value (`classinfo.cpp:154–166`) and walks the object's memory using **that class's field layout** (`classinfo.cpp:196`). The result is wrong chains baked silently into `GetInstance()`.

The hardcoded offsets are themselves labelled "Typical" (`classinfo.cpp:309–313`). If identification by vtable fails, they fall back to accepting any object with an in-module vtable as `"ClientGameContext"` (`classinfo.cpp:344–357`).

**Fix:**
- Require `TryIdentifyClassByVTable` (or a GetType call) to confirm the object's type before doing a field-based walk; otherwise use the blind walk.
- Log the confidence level in the generated header.
- Treat hardcoded offsets as hints that must pass type verification.

#### G11 (Medium): VTable-based class identification picks the first type reference it sees

`TryIdentifyClassByVTable` (`classinfo.cpp:839–895`) scans the first bytes of the first 50 virtual functions. It returns the class for **the first** RIP-relative `lea`/`mov` that points at any known TypeInfo or ClassInfo.

- **False positives:** functions that reference *other* types (`isKindOf` checks, factories, `GetType` of a member) appear earlier in the vtable than the class's own `GetType` and win.
- **False negatives:** the "stop at `0xC3`/`0xCC`" rule (`classinfo.cpp:861`) fires on ModRM or immediate bytes. For example, `mov eax, ebx` is `8B C3`.

`AnalyzeVTableMethod` already recognises the exact `GetType` shape, `lea/mov rax,[rip+x]; ret` (`classinfo.cpp:1597–1615`). Prefer that strict match; use the loose scan only as a fallback, and choose the most-derived class when several match.

#### G12 (Medium): Traversal is depth-first, so chains are not shortest and "instance" semantics are vague

- `BuildTraversalMap` and `BlindTraversalWalk` are depth-first and share one `visited` set (`classinfo.cpp:740`, `828`, `976`). An object first reached through a deep path is never expanded again through a shorter one. The "prefer shorter chains" checks (`classinfo.cpp:709`, `795`) only update that one map entry, never the object's descendants. Longer chains break more easily when the game changes. **Use breadth-first search.**
- Chains are keyed by the field's *declared* pointer type. For base types (`Entity`, `Component`, …), `GetInstance()` returns whatever object of some derived type happened to be found first. For non-singleton classes it returns an arbitrary instance, such as array element 0. The generated comment and the README should say this; `GetInstance()` suggests a singleton.

#### G13 (Medium): Root class gets a `return nullptr` stub unless literally named `ClientGameContext`

`DumpInstanceResolver` special-cases the root only when `className == "ClientGameContext"` (`classinfo.cpp:1382`). The traversal branch requires `!steps.empty()` (`classinfo.cpp:1394`), but root chains have no steps. When the root is identified by vtable under any other name, its own `GetInstance()` is emitted as `return nullptr`, unless `ScanGlobalsForSingletons` happened to find it separately. **Fix:** treat a chain with zero steps as "read the root global".

#### G14 (Medium): Header file names, `#include` names and class names disagree

- File names go through `GetSanitizedClassName`, but `#include "<parent>.h"` (`classinfo.cpp:1029`) and `ResolveHeaders` (`classinfo.cpp:1233`) use the **raw** name. Any type whose name contains `<`, `>` or `:` produces a broken include.
- Classes, structs and enums are declared with the raw name (`classinfo.cpp:1030`, `1035`, `1115`, `1159`), so the same names also produce invalid declarations.
- `headerFile[128]` (`classinfo.cpp:1004–1005` and its copies) silently truncates long names. The file is then written under one name while `SDK.h` includes another.
- On Windows' case-insensitive file system, `Foo` and `FOO` overwrite each other, while `SDK.h` includes both. Reserved device names (`CON`, `NUL`, `AUX`, …) would open devices instead of files.
- `ResolveHeaders` adds `#include`s for by-value member types that never get a header: types sent to the "Found data type" logging branch, or the `flags == 29` skip (`classinfo.cpp:257–264`).

#### G15 (Medium): Identifier collisions in generated code

Each of these causes a compile error once the relevant names occur:

- **Accessor vs. static functions.** A field named `Instance` or `TypeInfo` produces an accessor `GetInstance()` or `GetTypeInfo()` (`classinfo.cpp:1916`, `1937`, `1942`). These clash with the static `GetInstance()` and `GetTypeInfo()` (`classinfo.cpp:1371`, `1357`).
- **Duplicate member names.** Two fields that sanitize to the same identifier produce duplicate members, `Offsets` constants, accessors and `Defaults` entries. There is no de-duplication.
- **VTable struct.** `GetType` is not suffixed with its index (`classinfo.cpp:1610`), and `Get_<field>`/`Set_<field>` (`classinfo.cpp:1751`, `1758`) repeat for const/non-const overloads. The result is duplicate `static constexpr` names.
- **Enums.** All enums are unscoped and in the global namespace. Enumerator names that repeat across different enums collide once `SDK.h` includes everything. Consider `enum class`, or a namespace per enum.
- **CVars.** Sanitizing CVar names (`classinfo.cpp:3399–3404`) can map distinct names (`A.B`, `A_B`) to the same identifier.

#### G16 (Medium): `ConsoleVariables.h` references undeclared types, and `SDK.h` includes it first

For non-primitive field types, `typeStr = rawType` (`classinfo.cpp:3095`): enums, structs, `Int64`, `Uint64` and array types. The header only includes `FBSDKTypes.h` (`classinfo.cpp:3393`), and `SDK.h` includes it **before** any class header (`classinfo.cpp:2755`). Any such CVar therefore breaks `#include "SDK.h"`.

Pointer-typed members are also emitted as `T*` (a pointer to the pointee) instead of `T**` (a pointer to the pointer slot). And if the bonus-output phase fails, `ConsoleVariables.h` is never written, but `SDK.h` still includes it.

#### G17 (Medium): Typed virtual callers can use the wrong calling convention

`Call_Get_*` (`classinfo.cpp:1827–1830`) declares its return type from whatever field is found at the getter's offset (`classinfo.cpp:1739–1744`). If that field is a struct, the Microsoft x64 ABI expects a hidden return-buffer argument, but the detected function returns in `RAX`/`XMM0`. Calling the generated wrapper then corrupts memory. **Only emit typed callers for scalar and pointer return types.**

#### G18 (Low): `const char*` setters write caller pointers into engine-owned strings

`classinfo.cpp:1931` writes a caller's pointer into a field the engine owns. If the engine later frees or reallocates it, it crashes, and a stack buffer passed by the caller dangles. Document this or omit the setter.

#### G19 (Low): "TypeInfo" names actually point to ClassInfo

`GetTypeInfo()` (`classinfo.cpp:1354–1360`), JSON `typeInfoOffset` (`classinfo.cpp:2260`) and the IDA label `g_X_TypeInfo` (`classinfo.cpp:2478`) all emit the ClassInfo address (`c`), not `c->typeInfo`. Rename them, or emit both addresses.

#### G20 (Low): Base-class tail padding

A derived class assumes `sizeof(Base) == parent->totalSize` (`classinfo.cpp:1062–1066`). If the engine's size is not a multiple of the base class's C++ alignment, MSVC rounds `sizeof(Base)` up and the derived members move. The `static_assert`s from G1 would catch this. `TypeInfo::alignment` is read but never used.

#### G21 (Low): Enum forward declarations are ill-formed C++

`m_forwardDecls` contains `enum X;` (`classinfo.cpp:1155`, emitted at `2736`). Standard C++ does not allow forward-declaring an unscoped enum without a fixed underlying type; MSVC accepts it as an extension, but Clang and GCC reject it. Emit `enum X : int32_t` in both the forward declaration and the definition, or don't forward-declare enums. Separately, negative enumerator values are printed as `0xffffffff` (`classinfo.cpp:1200`), which changes the enum's underlying type.

#### G22 (Low): `//` comments can swallow the next line

Engine strings written into `//` comments (`classinfo.cpp:3406–3410`, `1403`, `1454`, `2081`) can end with `\`. A line ending in `\` is joined to the next line before comments are removed, so the next emitted line (for example, a `GetPtr_` definition) becomes part of the comment.

#### G23 (Low): Misc

- `DumpTemplateClass` (`classinfo.cpp:1953`) is dead code and duplicates `DumpStruct`.
- Timestamps in every generated header (`DumpHeader`, `classinfo.cpp:2012`) make diffs between SDK regenerations noisy.

### 2b. Generator runtime (stability inside the game)

#### R1 (High): Pattern scanner reads the whole image without fault protection

`FindPattern`/`DataCompare` (`main.cpp:11–50`) read every byte from the module base to `SizeOfImage`. There is no `__try` and no `VirtualQuery`. Protected or packed executables (Mirror's Edge Catalyst ships with DRM) and images with guard or `PAGE_NOACCESS` regions will raise an access violation, which **takes down the game**.

`FindPattern` is called from `ClassInfo::GetInstance` (`structs.h:190`) and up to 11 × 200 times from `FindClientGameContext` (`classinfo.cpp:507`). The displacement reads right after a match are also unguarded (`structs.h:194`, `classinfo.cpp:513`).

The `deref` branch (`main.cpp:41–45`) copies 4 bytes from the pointed-to address into a pointer-sized variable. That looks like a bug, but every caller passes `deref = false`, so it is dead code.

**Fix:** list committed, readable regions with `VirtualQuery` and scan only those. Wrap the scan loop in `__try`.

#### R2 (High): Many raw dereferences of engine memory outside SEH on the main path

`IsValidPointer` (`structs.h:32–37`) only checks the address range, not whether the memory is mapped. Yet most of the main dump path, which is **not** inside `GenerateBonusOutputs`' `__try`, dereferences engine pointers directly:

| Location | Raw dereferences |
|---|---|
| `DumpClasses` | `c->typeInfo`, `ti->name`, `ti->flags` (`classinfo.cpp:250–266`) |
| `DumpClass`, `DumpStruct`, `DumpEnum` | `strlen(ti->name)` (`998`, `1089`, `1142`) |
| `DumpEnumMembers` | `ti->fieldCount` (no upper bound), `fie->name`, `fie->value` (`1195–1201`) |
| `DumpClassMembers` | `*(TypeInfo**)mti->enumFields`, `ati->flags` (`1319–1321`) |
| `GetParents` | `p->parent` (`1339–1345`) |
| `BuildTraversalMap` | `fi->typeInfo->typeInfo`, `fieldType->flags`, `fieldType->enumFields`, `fi->offset` (`659–668`, `758`) |
| `BuildCrossRefMap` | `ti->fields`, `ti->fieldCount` (`2026–2030`) |

A single stale or garbage pointer anywhere in the reflection data crashes the game. The `Safe*` helpers already exist, but they are used inconsistently. **The structural fix is Q2:** copy everything into a validated in-process model once, using the `Safe*` helpers, and have every emitter work only on that copy.

#### R3 (Medium): Failures are silent and the success dialog is always shown

- `DumpClass`, `DumpStruct` and `DumpEnum` return silently when the file cannot be opened (`classinfo.cpp:1010`, `1099`, `1151`), without logging.
- `CreateDirectory` is not checked (`main.cpp:126`). `GetModuleFileNameA` is not checked in `FindClientGameContext` (`classinfo.cpp:298`).
- `GeneratorThread` always shows *"SDK generated successfully!"* (`main.cpp:144`), even if no file was written. One example is a DLL in a write-protected folder.

**Fix:** count headers written and failed, and errors swallowed by SEH. Show those counts and the log path in the final dialog.

#### R4 (Low): Reads of live engine state race with game threads

The generator walks live objects, linked lists and arrays from a background thread while game threads change them. SEH prevents some crashes but not torn or stale reads: freed memory can be reused and then misread as a valid object. This is inherent to the approach. Mitigations:
- Generate at a quiet point such as the main menu, which the README already advises.
- Validate more (for example, re-read the vtable after walking an object).
- Label every captured address and value as a snapshot.

Two small loop-bound issues: `for (addr = secBase; addr < secEnd - 8; …)` (`classinfo.cpp:565`, `2783`) skips the last pointer slot of each section.

## 3. Code quality

### Q1: One 3,500-line file and one class does everything

`classinfo.cpp` / `ClassInfoManager` handles finding the root object, heuristic class identification, graph traversal, x86 instruction matching, and nine output formats (C++ headers, `FBSDKTypes.h`, `SDK.h`, JSON, LiveDump, IDA, Ghidra, Cheat Engine, CVars). Suggested split:
- `discovery/`: pattern scanning, root finding, vtable identification, traversal;
- `model/`: a validated, plain-data type database;
- `emit/`: one file per output format, each reading only from the model.

### Q2: No intermediate model, so every emitter re-reads raw engine memory

The same engine structures are read again, each time with slightly different checks:
- 83 calls to `IsValidPointer` in `classinfo.cpp`;
- three different field-count caps: `1000` at `653` and `1560`, `10000` at `1267`, `1282`, `2026` and `2925`, and none at `1195`;
- the class/struct flag lists copied in four places (`253–264`, `2228`, `2294`, `2421`, `2539`);
- the vtable-capture block copied three times (`722–737`, `809–824`, `961–973`), and the third copy, unlike the others, calls `AnalyzeVTableMethod` even when `entry == 0`.

Reading everything once into `struct TypeDb { std::vector<Type>; … }` would fix R2, remove the duplicates, make the emitters easy to unit-test without the game (Q8), and give every output the same consistent view of the data.

### Q3: Magic numbers

Flag values (G9), per-game offsets, scan windows (`0x200`), score thresholds (`3`, `5`), depth limits (`5`, `4`) and buffer sizes all appear inline without names or explanation. Name them and document where they came from.

### Q4: Dead and unused code

- `DumpTemplateClass` (never called).
- `FindPattern`'s `deref` branch.
- Emitted but unused helpers: `fb::WeakPtr`, `fb::String`, `fb::ReadPtr`.
- `volatile char c1, c2` (`classinfo.cpp:2215–2216`, which trigger unused-variable warnings).
- `MemberInfoFlags` constants, `TypeFlags::kTypeFlag_Enum`, `ClassInfo::id3`, `TypeInfo::flags2`, `TypeInfo::alignment` (useful for G20).
- `ConsoleVariableInfo::rva` is calculated for Source 1 entries but not used when `globalOffset > 0`.

### Q5: Inconsistent safety idioms

`SafeRead*` helpers sit alongside raw dereferences (R2). `__except(1)` and `__except(EXCEPTION_EXECUTE_HANDLER)` are mixed. Both `SafeCountVTableEntries` and `TryIdentifyClassByVTable` cap their loops, at different values (256 and 50). Pick one approach and use it everywhere.

### Q6: Formatting and text hygiene

- `ScanGlobalsForSingletons` is indented with spaces; the rest of the code uses tabs.
- `classinfo.h` contains mojibake (`â€”`, `â†’`): UTF-8 that was decoded as Windows-1252 and saved again (`classinfo.h:8`, `188`, `201`, `205`, `211`).
- `structs.h:129–130` repeats a doc comment.
- The auto-generated XML doc comments add nothing ("Datas the compare.", `main.cpp:8`).
- Section headers still say "(unchanged)" and "(unchanged from v1)" even where the code has changed.

### Q7: Build files are stale and contradictory

- `FrostbiteGen.vcxproj` targets the `v140` toolset (VS2015) and Windows SDK `8.1`. Its `Win32` configurations build an **Application** rather than a DLL (`FrostbiteGen.vcxproj:28`), and it does not set `/EHa` (S4). It is also listed in `.gitignore`. Either delete it in favour of CMake, or regenerate it from CMake.
- `CMakeLists.txt` does not check for x64 (add a `CMAKE_SIZEOF_VOID_P EQUAL 8` check), does not set warning levels (`/W4`, `/permissive-`), and does not treat warnings as errors in CI. Several issues in this report would show up as warnings, for example signed/unsigned comparison at `classinfo.cpp:858` and passing a pointer to `%llX` at `structs.h:198`.

### Q8: No tests at all

Much of the code is pure and easy to test offline:
- `SanitizeMemberName`, `EscapeJson`, `EscapeXml`, `GetSanitizedClassName`;
- `AnalyzeVTableMethod` and the identification logic, fed byte buffers;
- the emitters, fed a synthetic type database.

**Highest-value test:** build a fake type database with an `Int64` field, an array field, a struct field, an integral-valued float, an enum, a class with 26 virtual functions and a few hostile names. Generate an SDK from it and **compile it** in CI with MSVC (and Clang for portability). This alone would have caught G1–G4, G14–G16 and G21.

### Q9: Misc hygiene

- Mutable globals `g_szLogFile` and `g_szBaseDir`.
- `std::localtime` and `std::asctime` are not reentrant; harmless with one thread.
- `GetFixedClassName` returns a `const char*` that may point into engine memory.

## 4. Performance

All of the following runs on a background thread inside the game, so costs show up as long generation times and competition for game CPU rather than a frozen UI.

### P1 (High): CVar anchor search does an SEH-guarded read per byte of the whole image, 10 times

`DumpConsoleVariables` (`classinfo.cpp:3320–3345`) calls `SafeReadBytes(p, &c, 1)` for **every byte** of **every readable section**, once for each of 10 anchor strings. Each call is a function call with an SEH frame. For a 100–200 MB image that is roughly 10⁹ guarded calls, likely minutes of CPU time.

**Fix:** list readable committed regions once with `VirtualQuery`, then search for all anchors in a single pass with `memchr`/`std::search` (or a `boyer_moore_horspool_searcher`) inside one `__try`.

### P2 (Medium-High): Singleton scan tries to identify a class for every 8-byte data slot

`ScanGlobalsForSingletons` (`classinfo.cpp:2774–2847`) calls `TryIdentifyClassByVTable` for each 8-byte slot of every initialized and uninitialized data section, including `.rdata`, which contains vtables and strings. Each call can read up to 50 vtable entries, copy 32 bytes of code per entry, scan it byte by byte and do map lookups.

**Fix:**
- Scan only writable sections.
- Cache vtable → ClassInfo once per vtable address. There are far fewer distinct vtables than slots, so this removes most repeat work.

### P3 (Medium): Brute-force root scan

`FindClientGameContext` (`classinfo.cpp:565–599`) does 2 × 63 guarded reads for every heap pointer in every writable section. It would also benefit from the vtable cache.

### P4 (Medium): Naive, repeated pattern scanning

`FindPattern` compares byte by byte with a mask string. `FindClientGameContext` runs it for 11 patterns, restarting from `match + 1` up to 200 times each, which is effectively a full scan per pattern. Match all patterns in one pass, filtering first on the first byte with `memchr`.

### P5 (Medium): `Log` opens, appends to and closes the log file on every call

`main.cpp:55–85`. Traversal, diagnostics and verbose vtable logging produce thousands of lines. Keep a single buffered stream open, and flush on errors and at the end.

### P6 (Low): No memoization of vtable analysis

`TryIdentifyClassByVTable` and `AnalyzeVTableMethod` re-analyse the same vtables and functions every time they are seen. Cache by vtable or function address.

### P7 (Low): Generated SDK compile cost

Every class header carries its own `VTable` struct, `Defaults` struct, three hook templates and full accessor sets, and `SDK.h` includes every header. With thousands of types this makes builds that include `SDK.h` very slow. Options:
- move the hook templates into `FBSDKTypes.h` once;
- make `Defaults`, `VTable` and the hooks opt-in via `#ifdef`;
- keep encouraging per-header includes, as the README's "Option B" already does.

Minor: `for (auto it : m_classMap)` copies a `std::string` per entry (`classinfo.cpp:245`); `std::vector` traversal chains are copied per field visited.

## 5. Accessibility

FrostbiteGen has very little user interface: one `MessageBox` and a log file. The generated SDK is source code. Accessibility concerns are therefore narrow but real.

### A1: The only result feedback is an ownerless MessageBox

`main.cpp:132` and `main.cpp:144` call `MessageBox(0, …)` from a background thread. While a game runs in exclusive fullscreen, the dialog may appear **behind** the game. Keyboard and screen-reader users then cannot reach or notice it, and the game may appear frozen to them.

- Add `MB_SETFOREGROUND | MB_TOPMOST`.
- Write a clear final summary line to `fbgen.txt`.
- Optionally play an audible cue (`MessageBeep`).

The error text "Failed to find ClassInfo" is not actionable. Include the log file path and the next step, for example "wait for the main menu and inject again".

### A2: README relies on box-drawing diagrams

The directory trees and the architecture diagram use `├──`, `│` and `▼` (README "Step 4", "SDK Architecture"). Screen readers read these badly or as noise. Add a short prose or nested-list version next to each diagram. Mark the diagram blocks as `text` so assistive tools and syntax highlighters treat them consistently.

### A3: Generated artifacts

No accessibility issues beyond what is noted above. The Cheat Engine table sets `DisplayMethod="Unsigned Integer"` for every field, including floats (`classinfo.cpp:2965`), which shows them as meaningless numbers. Map float and double fields to CE's `Float`/`Double` var types. This is usability more than accessibility.

## 6. Documentation drift (README vs. code)

### D1 (High for users): README documents helpers that are not generated

README Examples 4 and 5 and the "SDK Architecture" diagram use `fb::ReadChain` and `fb::PatternScan`. `GenerateFBSDKTypes` (`classinfo.cpp:2638–2722`) emits neither. Following the README produces code that does not compile. The generator itself even emits a comment pointing users at `fb::PatternScan()` (`classinfo.cpp:1425`).

### D2 (Medium): README describes an instance-resolution mechanism that no longer exists

These README sections all describe an older design:
- "Automatic Instance Resolution"
- "How Instance Resolution Works"
- the sample `fbgen.txt` line *"Discovered instance offset in ClassInfo: 0x48"*
- Troubleshooting: *"WARNING: Could not reliably discover instance offset"* and *"manually set `m_instanceOffset` in the `ClassInfoManager` constructor"*

That design read `*(ClassInfo + 0x48)` inside `__try` and checked `IsValidPtr`. The current code has no instance-offset probing, no `m_instanceOffset`, and a different emitted `GetInstance()` that uses traversal and global singletons (`classinfo.cpp:1367–1431`).

### D3 (Low): Output listing is out of date

- `Array.h` is listed but never generated; `Array` lives in `FBSDKTypes.h`.
- Not listed: `sdk.json`, `LiveDump.json`, `ida_import.py`, `ghidra_import.py`, `CheatEngineTable.CT`, `ConsoleVariables.h`, `CVars.json`, `CrossReferences.h`, `ClassHierarchy.h`.

### D4 (Low): `/EHa` claim is inaccurate

The README says `/EHa` is "Required for `__try/__except`". It isn't: MSVC supports SEH without it. `/EHa` makes C++ destructors run during SEH unwinding and lets `catch(...)` catch SEH exceptions. Keep the flag, which is good for S4, but fix the reason given.

### D5 (Low): Toolchain mismatch

The README requires VS2022 and CMake; the tracked `.vcxproj` is VS2015-era (Q7).

### D6 (Low): Overclaims

"Correct Memory Layout… exact in-memory structure" and "no manual reverse engineering required" are contradicted by G1, G7, G8 and the hardcoded per-game offsets. Soften these claims, or back them with the `static_assert`s from G1.

## 7. What is done well

- **Loader-lock safety:** the work runs on a thread created from `DllMain`, which also calls `DisableThreadLibraryCalls`, and the thread unloads the DLL with `FreeLibraryAndExitThread`.
- **Guarded read helpers** (`SafeReadPointer`, `SafeReadString`, …) are correctly kept free of C++ objects so MSVC accepts `__try` in them.
- **Cycle detection** in the class list, the parent chain and traversal.
- **ASLR-relative addresses** everywhere in the output.
- **Escaping** for JSON and Cheat Engine XML, and **path sanitization** for header file names.
- **Many output formats** (IDA, Ghidra, Cheat Engine, JSON) from a single run is genuinely useful. A shared validated model (Q2) would make them reliable.
